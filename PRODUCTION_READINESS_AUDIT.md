# SyncLiving production readiness audit

**Audit date:** 2026-10-04  
**Decision:** **Not ready for production.** The code has useful security and build improvements, but no safe staging database or deployment target is configured. Critical database security findings remain open in the connected Supabase project, legal notices are still drafts, and live end-to-end authorization has not been verified.

## Changes made in this audit

- Tightened apartment-admin tenant checks and removed duplicate exported admin handlers that could override scoped versions.
- Made vendor assignment atomic and same-complex; scoped admin user updates and rejected unassigned apartment admins.
- Denied visitor QR verification for unassigned admins/guards, restricted pass creation to assigned residents, and made QR check-in/scan counting a single row-locked transaction. Added API/unit regression coverage.
- Made security-guard pass check-in and check-out tenant-scoped conditional updates, so membership and current pass state are checked in the same database statement. Added API regressions.
- Hardened Razorpay webhook verification and redacted payment references from routine logs.
- Traced the login TLS failure to PostgreSQL on the configured Supabase shared pooler; added a verified project-CA configuration path, forbade plaintext/disabled verification, and made server errors safe for login clients while recording TLS code/message in server logs.
- Removed assistant prompt, response, and database result contents from logs; reduced production error and audit log detail.
- Kept authentication profile/context data in memory instead of `localStorage` and clear legacy stored values on startup/logout.
- Gated in-process scheduled jobs behind `ENABLE_IN_PROCESS_SCHEDULER=true`; uniform maintenance invoices additionally require `ENABLE_UNIFORM_MONTHLY_MAINTENANCE_INVOICES=true` and a configured amount.
- Excluded `credentials.txt`, seed scripts, test data, and local report artifacts from the Docker build context. The credentials file is ignored by Git and Docker; it was not read or changed.
- No Supabase accounts or records were modified or deleted. Super Admin identity, permissions, settings, and associated data were left untouched; no test or sample data was removed.
- Lazy-loaded route components. The initial JavaScript bundle is now about 287 KB (94 KB gzip); the largest chart chunk loads separately.
- Updated CI to validate rather than deploy automatically. No database migration or deployment was run.

## Connected Supabase project — read-only review

No destructive data cleanup or account changes were made. The only schema change during login repair was the additive migration `014_refresh_session_rotation.sql`, applied transactionally to create the missing refresh-session table and its indexes/policies; it did not alter existing users or other application records. The connected project currently has no development branches. A Supabase branch was quoted at **$0.01344/hour**, but branch creation was rejected because branching requires the Pro plan or above. No plan upgrade or paid resource was created. The project reports PostgreSQL `17.6.1.084`; Supabase announced PostgreSQL `17.11` on 2026-09-25 to address 44 CVEs, with a dashboard upgrade available from 2026-09-28. Read-only checks found UTF-8/ICU collation, no `ltree` or `btree_gist` extension/index candidates, no custom operators with non-built-in estimators, and `pgcrypto` installed. Source search found no `pgp_*` encryption calls, but did not inspect arbitrary encrypted values in the database. Review the official [release notice](https://supabase.com/changelog/postgres-15-19-17-11-breaking-changes) and check any externally encrypted data before an authorized maintenance upgrade. Applied migrations include `enable_rls_with_role_scoped_policies`, `monetization_analytics`, `restrict_monetization_data_api`, `add_monetization_fk_indexes`, and `refresh_session_rotation`. Local migrations `012` and `013` remain unapplied.

**Login TLS incident:** The frontend sends `POST /api/v1/auth/login` through the Vite `/api` proxy to the Node API. The login controller's first operation is a PostgreSQL query, not a Supabase Auth or Storage HTTPS request. Local backend request logs showed two login 500s at 14:41:59 and 14:42:05 on 2026-10-04. A credential-free PostgreSQL SSL negotiation against the configured Supabase shared pooler (`aws-1-ap-south-1.pooler.supabase.com:6543`) reproduced `SELF_SIGNED_CERT_IN_CHAIN`; the Windows system CA store also rejected it. The supplied `prod-ca-2021.crt` parses as the self-signed Supabase Root 2021 CA (SHA-256 fingerprint `80:70:25:AD:50:D4:ED:21:9D:2C:9C:7D:29:9C:00:4F:82:4E:B0:0C:F7:F6:5A:FE:F6:07:D0:7B:72:E6:CA:FA`) and successfully verified the live pooler certificate for `*.pooler.supabase.com`, issued by Supabase Intermediate 2021 CA, with hostname and chain checks enabled. `DATABASE_SSL_CA=certs/prod-ca-2021.crt` now loads that ignored local certificate through a project-root-relative path. The backend restarted with the setting; `SELECT 1` and `/health` both succeed. A no-match login probe through the Vite proxy reached the database and returned the expected 401 without creating a user or session. The existing Super Admin login was not attempted because it needs the real password and a successful login writes a refresh-session row. See [Supabase's SSL connection guidance](https://supabase.com/docs/guides/database/connecting-to-postgres).

**Login 500 follow-up:** After PostgreSQL TLS was fixed, the backend log recorded SQLSTATE `42P01` (`undefined_table`) for login. The user, complex, unit, and user-unit tables existed, but `auth_refresh_sessions` did not; the failure occurred at the final refresh-session insert after account lookup, password comparison, and token signing. Applying migration `014_refresh_session_rotation.sql` restored the required table. Post-migration checks confirmed RLS and the expected server-side insert grant, and the table remained empty after a wrong-password diagnostic probe. The restarted backend reports healthy and the same probe now returns the expected 401 instead of 500. No real-password login was submitted during verification, so a successful interactive Super Admin login remains for the account owner to confirm.

The Supabase advisors currently report:

- 13 tables with RLS enabled but no policies: buildings, complexes, invoices, parking requests/vehicles, payments, Razorpay transactions, units, user-unit links, users, vendor requests/vendors, and visitor parking sessions.
- 19 tables discoverable to the `anon` role and 19 to `authenticated` through GraphQL because those roles retain `SELECT` grants.
- Four functions with mutable `search_path`: `update_updated_at`, `jwt_user_id`, `jwt_role`, and `jwt_complex_id`.
- Six tables with multiple permissive policies, 21 unindexed foreign keys, 39 indexes not observed in use, and two duplicate index pairs (invoices and payments). Low traffic can make unused-index reports misleading; do not drop indexes without query review.

Migration `013_restrict_public_data_api_grants.sql` is intended to revoke direct browser-role table/sequence/function privileges and pin the helper-function search paths. It is still **unapplied**; verify the Node API's required database role and run role-based tests on staging before applying it. Advisor references: [RLS enabled without a policy](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy), [mutable function search path](https://supabase.com/docs/guides/database/database-linter?lint=0011_function_search_path_mutable), [anonymous GraphQL exposure](https://supabase.com/docs/guides/database/database-linter?lint=0026_pg_graphql_anon_table_exposed), [authenticated GraphQL exposure](https://supabase.com/docs/guides/database/database-linter?lint=0027_pg_graphql_authenticated_table_exposed), [unindexed foreign keys](https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys), [unused indexes](https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index), [multiple permissive policies](https://supabase.com/docs/guides/database/database-linter?lint=0006_multiple_permissive_policies), and [duplicate indexes](https://supabase.com/docs/guides/database/database-linter?lint=0009_duplicate_index).

An earlier read-only snapshot showed no users, complexes, subscriptions, or platform-payment rows; it did show 20 platform usage events. A later targeted read-only check verified the active Super Admin account described above. Neither check is proof of a production backup or a complete inventory. No staging branch exists, so migrations `012` and `013` and live role-isolation workflows remain unvalidated.

The connected project's branch feature is unavailable without Pro and the quoted rate was $0.01344/hour; do not upgrade or create paid resources under the current constraint. No Docker, `psql`, or Supabase CLI is available in this environment for local PostgreSQL staging. 3. Create and verify a staging super-admin account. `credentials.txt` is present but ignored/excluded; no credentials were supplied in this request, so it remains unchanged. Do not seed the connected remote project.
4. Implement and test the actual platform subscription payment/ledger write path; verify both provider keys and webhook delivery on staging before reporting collected revenue.
5. Decide on a backwards-compatible QR-token protection and rotation plan; verify check-in/out concurrency on PostgreSQL staging; configure email/SMS; and define retention/deletion handling.
6. Replace legal placeholders and draft version strings with reviewed provider details/notices. Configure support, privacy, and grievance contacts.
7. Choose the host, configure exact HTTPS CORS origins and production secrets, select one scheduler or an external job runner, complete backups/restore and monitoring checks, deploy a private preview, and perform responsive desktop/mobile smoke tests before production approval.

**Rollback/recovery:** No database or deployment changes were made, so there is no deployment to roll back. Before future migration/deploy work, take/verify a recoverable database backup, preserve the current application image/revision, test migration rollback/forward strategy on staging, and use the host's previous deployment revision for application rollback.
